# 把 MovieRoll 迁移到别的代码库

英文版是 `SKILL.md`;`references/` 下的参考资料只有英文一份。

本仓库是**源**,在迁移过程中对它只读。目标可以是任何东西:另一个 DiT、另一个框架、另一套训练栈。正因为目标未知,
这项工作从**读目标**开始,而不是从拷文件开始。

| 文件 | 内容 |
|---|---|
| `references/modules.md` | 十一个可迁移单元:各自做什么、在本仓库哪里、宿主必须提供什么、不变量,以及「Porting a single unit」一节里的「能力 vs 语义」对照表和只迁一两个单元的场景表;图生视频写在 P7、P8 和 P10 的 ACS 变体里 |
| `references/survey.md` | 面对陌生目标要回答的问题、怎么找到答案、每个答案会改变什么 |
| `references/verification.md` | 门禁,以训练态/推理态等价为核心 |

## 要带过去的那一个核心想法

其余全都是围绕它的细节:

> 模型是**一个**函数,用在两种形态下。训练时干净历史作为输入 token 进来,推理时它存在 KV cache 里。
> 两种形态下,每个 token 必须看到同一组 KV 条目、以及同样的 RoPE 相对距离。

破坏它不会报错。形状对得上、loss 在降、出图看着也正常,而模型学到的分布和部署时跑的不是一个。这就是
`references/verification.md` 把等价性当作首要门禁、并且认为"拿输出跟 MovieRoll 对拍"没有意义的原因 ——
目标的权重不一样,根本不存在可以对拍的参考视频。

有一个例外值得先知道:只做推理侧的迁移跑不了那个门禁,因为它只有一种形态。那种情况下,顶替它的是
"退化配置下逐位一致"和"与显式 mask 实现对拍"。

## 流程

### 1. 先勘察目标

按 `references/survey.md` 走一遍,只读。计划定下来之前不要往目标里写东西,也永远不要往本仓库里写。把答案按
`问题 → 答案 → 影响` 记下来并给用户看。

先问那份文件里的 **Question 0:模型还会不会重训?** 由它决定的事比别的任何一条都多:只做推理侧的迁移意味着
训练侧的单元都不在范围内、G2 等价性门禁**根本跑不了**,而且 P7 单独能达到的效果有上限。

勘察的结论是给宿主归类,而类别决定了工作量:

- **cross-attention DiT** —— 只迁纯图像的注意力 kernel;"历史与文本无关"这条不变量自动成立
- **MMDiT** —— 和本仓库一样;两套 kernel 都要迁
- **已经是块因果且带 KV cache** —— 便宜又划算的子集是 context noise + HieraKV + recompute + AnnealCFG,
  完全不用改训练配方
- **双向、非因果** —— 整套都要,而且要预料到"拆开 KV cache 的读写路径"和"逐帧 scheduler"是两处最难的改动

### 2. 和用户商定子集

**多数单元都能单独迁。** 不要默认全迁,也不要因为依赖图上有一根箭头就扩大范围 —— 那张图画的是"谁能加强谁",
不是"谁必须跟谁一起走"。这一步该用的是 `references/modules.md` 里的那张表和场景表。

用户**点名某一两个单元**时,照那份文件「Porting a single unit」一节末尾的四步走:

1. 读该单元的 **Standalone?** 和 **Add another unit only if** 两行;
2. 把它要求的每项**能力**对照你的勘察结果核一遍;
3. 只有宿主确实不具备的能力,才提议追加对应单元,并说明代价;
4. 如果那是**语义**依赖而不是能力依赖(最典型的是 P7 缺 P8),就明说并让用户定,不要悄悄把一件训练侧的活
   塞进一个推理侧的需求里。

用户只说**目标**时用场景表:cache 无界是 P3(+P4);漂移只需要 P5;多步采样质量一般是 P6;解码开销是 P11;
"这套方法值不值得"是 P2 的 mask 退化版加 P7 当测量手段;"已经蒸出了少步模型,想让长视频 rollout 撑得住"是
P10,用宿主自己的少步模型代替 P9 当起点(仍然需要 P7;本仓库没有块式的 CuLT-DMD)。图生视频不是单独的单元:
推理用的是 P7 的 i2v 布局,训练靠 P8 按概率抽到的 i2v 步;只有要蒸馏 i2v 模型时,才再加上 P10 下的 ACS。

选择和理由都要记下来。**只迁一个单元是一件完整、可交付的工作**,它不必长成整套。

### 3. 按依赖顺序,一次只迁一个单元

每个单元:读 `references/modules.md` 里它那一节,根据勘察结果找到宿主的插入点,用**宿主自己的写法**写代码,
加开关保证可回退(G0),然后跑完它的门禁再开始下一个。没过门禁的单元不算做完;在没验证的第一个单元上面叠第二个,
会让故障没法定位。

只迁一个单元时顺序问题自然消失,但门禁不能省:跑 `references/verification.md` 门禁表里它那一行 ——
那张表对"单独迁"的单元列的是精简集。

新代码放在目标仓库里独立的目录或模块下,不要把改动零散撒在各处,这样这次迁移才是可审查、可回退的。

### 4. 验证

按 `references/verification.md` 做。G2 等价性测试要**早**建 —— 在依赖它的那些单元之前 —— 因为它是唯一能抓到
那个真正要命的失效模式的检查。

### 5. 记录

决策记录和进度表放在本仓库之外:计划定下来之前放在你自己的临时目录里,定下来之后如果用户愿意,再挪到目标仓库里、
和迁过去的代码放在一起。要记下:选了哪些单元、哪些门禁过了、数字是多少、还有什么没解决,以及每一个因为勘察回答
不了而不得不做的假设。这里一个没记下来的假设,会在几个单元之后变成一个静默的数值 bug。

## 硬规则

1. **迁移过程中绝不往本仓库写任何东西。**
2. **本仓库的代码是真值。** `references/modules.md` 和代码冲突时,代码是对的,该改的是文档。
3. **是适配,不是移植整套。** 复用宿主的 trainer、scheduler、VAE、文本编码器和并行方案。把 MovieRoll 的框架
   连同逻辑一起搬过去,结果是两套半残的栈。
4. **任何东西都不能依赖 rank。** 所有影响形状的抽样都在 sp 组 rank 0 上抽完再广播。依赖 rank 的分支、或者在
   某个 rank 上多抽一次,都不会报错,它会让集合通信错位然后卡死。
5. **一个单元,一轮门禁。** 不在没验证的工作上面继续叠。
6. **勘察回答不了、而又会影响设计的问题,停下来问。** 不要默默选一个约定;把问题记下来、给一个缺省建议、
   让用户确认。
7. **不要自行扩大范围。** 用户要一个单元,就交付那一个。只有宿主确实缺某项能力时才提议追加单元,并说明代价 ——
   不能因为依赖图上有箭头就加,也不能为了让迁移"完整"而加。
8. **不要顺手重构目标仓库里无关的部分**,也不要在没被要求时去那边 commit 或 push。

## 工作循环

```
- [ ] 1. 勘察目标(references/survey.md),记录答案,给宿主归类
- [ ] 2. 商定单元子集:点名了单元就核对能力、不额外加东西(要加须说明理由);只给了目标就查场景表
- [ ] 3. 子集里有需要 G2 的单元时,先把 G2 等价性测试搭起来
- [ ] 4. 按依赖顺序逐个单元:读那一节、加开关插入、跑它的门禁
- [ ] 5. 记录门禁、数字、未决问题和假设
```
